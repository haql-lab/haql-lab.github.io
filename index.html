The cost

A volume error does not stay an error.

It gets filed. It gets reported to a partner. It gets netted against a royalty owner who did not agree. By the time someone catches it, the correction is a letter, an amended report, and a reconciliation meeting.

The filing is rejected

A monthly state filing is a legal document built on volumes. A wrong disposition code or a missed stock change gets it rejected — and you resubmit, late.

The partner dispute

A joint-venture partner queries a volume. You pull the export. You cannot prove which figure was right on the day it was received, because the correction was made on a guess and the trail is gone.

The month-end scramble

Mismatches surface in the last two days. Now someone is re-keying numbers at 9pm, and the person doing it is not the person who will defend the number in April.

The silent pass

Fifteen thousand rows cannot be eyeballed. Scanning finds what looks wrong. Row thirteen thousand looks exactly like a correct row when you are scanning.

haql-qc

Data quality

Checks each record for physical impossibilities and structural problems before the data is trusted. Every finding carries a permanent rule ID, the 1-indexed source row, and the SHA-256 of the input file.

Goes in

Production CSV — daily or monthly period. Well and date columns identified. Units declared by you, never guessed from a column name.

Comes out

JSON or JSONL audit report: findings by rule and severity, per-well medians used for materiality, and a run-level SHA-256 so you can prove which bytes were audited.

What it actually catches
  • Missing or unparseable identifiers — a row that cannot be attributed to a well
  • Negative production volumes — not realisable; flag whether produced or injected, because the sign convention differs
  • Cumulative totals that decrease — impossible without a documented reset
  • Shut-in contradictions — zero uptime while still producing at normal rate
  • Date gaps — judged against each well's own cadence, not a global assumption
  • Plausibility breaches — decimal errors and unit mix-ups, not performance judgements

Materiality is measured against the well's own median. 0.003 Sm³ is nothing on a well producing 6,000 Sm³/d and an emergency on one producing 5. That is why 4 findings are high and 34 are informational.

Proprietary, source-available. Full Python source published so you can read exactly what it does to your data. Evaluation use needs no key. 237 tests, all offline.

haql-closeout

Month-end

Runs at the end of the period and answers one question: is this month complete and reconciled enough to lock? Reconciliation checks that a per-record QC pass cannot do.

Goes in

The same production CSV, plus well test rates, downtime reason codes, and field-level sales or disposition volumes where you have them.

Comes out

Closeout report naming the wells and days that block a clean close, each with rule ID and source row.

What it actually catches
  • Well test vs. daily average — a test rate that does not reconcile with reported daily volumes
  • Downtime vs. production — a well recorded shut-in while volumes say it was running
  • Date continuity — reporting gaps measured against that well's own established cadence
  • Field balance — volumes sold or delivered exceeding what the field produced
  • Cumulative continuity — totals that go backwards inside the period
  • Duplicate well-days — the same well reported twice for one date

Same design stance as haql-qc: read-only, offline, deterministic, traceable to the row.

Proprietary, source-available. Best run after haql-qc — QC clears the records, closeout confirms the period ties out.

On regulators and filings. These tools do not generate regulator-specific forms, and they do not know any state's format. They check the volumes those forms are built from — and they are jurisdiction-agnostic, so the same rules apply whether your wells are in Texas, Alberta, or the North Sea. If you need a state-specific formatter, say so and I will tell you honestly whether I can build it.

How it works

One step added. Nothing replaced.

  1. ExportProduction data from whatever you already use — no change to your capture or accounting system.
  2. Send or runEmail me the file for a free sample, or run the CLI yourself. Nothing is installed either way.
  3. ReviewEvery finding names the rule, the well, the date and the row. Open the CSV and look.
  4. FixYou correct your source of truth. The tool never writes to your file.
  5. File or closeWith a report that shows what was checked and what was found.
Same rules every time

Deterministic. Identical bytes give an identical report — no variance run to run, which is what makes it defensible in an audit.

Every finding cites its row

Rule ID, 1-indexed source row, observed value, and the input SHA-256. "There was a problem" is not actionable; row 1984 is.

Runs offline

No network call, no telemetry, no upload. Reservoir data frequently cannot leave your infrastructure, so the tool never asks it to.

It says when it does not know

No unit declared means no unit-dependent check runs, and the report names the gap. It will not guess a unit and put a false claim in the audit record.

About

Why you should hand over a month of production data to a stranger.

Fair question. Here is the actual answer.

I build reservoir and production software, and I publish the source. The haql-qc package ships its complete Python source — the rules, the loader, the audit schema. You can read exactly what it does to your file before you run it. That is also why the rules are numbered permanently: adding a rule never renumbers an existing one, because audit logs referencing them are already in other people's hands.

Three commitments shape the work, and they are the reason a rule that cannot be certain says so rather than guessing:

  • Never corrupt source data. The tool is read-only by construction. It cannot auto-correct, because correcting requires knowing which of two contradictory fields is wrong, and the data cannot supply that.
  • Never guess. A confidently wrong unit is worse than no check at all. Units are declared by you and recorded in the report as your declaration.
  • Never be untraceable. Every finding ties to a stable rule ID, a row you can open in an editor, and a hash of the input.

Validation is against one public field — Volve, 15,634 daily rows and 526 monthly rows. One field is a starting point, not a general guarantee, and I will not claim otherwise. No Volve data is bundled with the package; it downloads nothing.

FAQ

Straight answers.

Does it use AI?

No. Every rule is deterministic arithmetic on your data — comparisons, monotonicity checks, medians. No model, no network call, no language model anywhere in the package. Running the same file twice gives the same answer.

Does my data leave my computer?

Run locally, nothing leaves your machine — the code makes no outbound calls, and you can confirm that yourself in the published source. If you use the free sample check instead, you are choosing to email me the file, and you can ask for it back anonymised or deleted.

What do I need to install?

Nothing, if you use the free sample check — email the file, I send the report. To run it yourself you need Python 3.9 or newer and nothing else; the audit engine is standard library only. Spreadsheet input needs one optional extra package.

What file formats?

Production CSV for daily and monthly period exports. Monthly files that declare their own units in a second header row are read directly. XLSX, ZIP, JSON, JSONL, DBF and fixed-width are supported through the ingest layer.

Can I try it free?

Yes. Email me one month of data — anonymised if you prefer — and you get the full report at no cost. Evaluation use of the CLI also needs no license key.

How is it licensed?

haql-qc and haql-closeout are proprietary and source-available: full source published, running it commercially requires a license. Licenses are signed ed25519 tokens carrying company, tier, seats and expiry, verified entirely offline against an embedded public key — no activation server, no phone-home. haql-units and haql-coords are MIT and need no license at all.

One offline check cannot tell whether a revoked license was revoked — why?

Because nothing inside the token records that fact. A revoked license verifies correctly until it expires, unless the caller checks a registry. I would rather state that limit than imply revocation works offline when it does not.

Will it decide whether my well is performing?

No. Plausibility is not performance. It flags a reading of 500,000 bbl/d as a decimal error, not as unusual, and it refuses questions outside its competence.
