haql-engine · deck and grid support

The deck is the input. Now more of its properties are too.

The native solver still runs the SPE1 CASE1 driver. This increment moves the property and static-grid layer off hard-coded SPE1 constants: fluid tables come from the deck, includes are resolved, COPY/MULTIPLY is applied, and the standard 9,000-cell SPE9 grid assembles.

What changed

Before this increment, blackoil_vs.PVT() carried the SPE1 PVT and relative-permeability tables as module constants. That was correct for SPE1 and misleading for every other deck. The engine now accepts a deck's own tables:

Deck keywordNow used for
PVTOSaturated Rs, Bo, mu_o and undersaturated Bo(p,Rs), mu_o(p,Rs)
PVDGBg(p), mu_g(p)
PVTWBw(p), mu_w(p)
SWOF / SGOFThree-phase water/gas/oil relative permeability
DENSITYSurface densities and gravity

PVT() still gives the historical SPE1 tables. A regression test asserts that the SPE1 deck tables are bit-identical to those defaults, so existing SPE1 results do not move.

Deck reading is broader, but still bounded. deckparse.py now resolves recursive INCLUDE files relative to the including deck, detects include cycles, expands N*value and N*, and applies COPY/MULTIPLY array operations, including optional six-index I/J/K regions.

Why SPE9, not corner-point first

The standard SPE9 deck is Cartesian: 24 × 25 × 15 = 9,000 cells. Its published grid uses DX, DY, DZ, TOPS and PERMX, not corner-point COORD/ZCORN. Starting with corner-point geometry would add geometric risk before the property and schedule layers are deck-driven.

The real SPE9 blockers are the tables and the schedule: 25 producers, one water injector, WELSPECS/COMPDAT, wildcard well names, WCONPROD/WCONINJE, and a 900-day sequence of rate periods. This increment closes the static-grid and property part. The schedule and native time-stepping are the next increment.

How to use it

from deckparse import parse
from deckprops import tables_from_db
from blackoil_vs import PVT
from fieldgrid import build_cartesian

db = parse("benchmark/decks/spe9/SPE9.DATA")
pvt = PVT(tables_from_db(db))
grid = build_cartesian(db)

print(grid.nx, grid.ny, grid.nz)   # 24 25 15
print(grid.n)                       # 9000
print(pvt.density)                  # SPE9 DENSITY

The table builder accepts optional undersaturated PVTO continuations in the usual p Bo mu_o form. PVT validates monotonic pressures and saturations, positive densities and positive water properties, and reports a clear error instead of falling back to SPE1 values.

The SPE9 static grid

fieldgrid.build_cartesian assembles and validates the standard SPE9 geometry:

  • 24 × 25 × 15 cells, 9,000 active cells;
  • 300 ft in x and y;
  • the 15 published layer thicknesses from 20 ft to 100 ft;
  • TOPS per column, including the 10-degree x-direction dip;
  • PERMX, PERMY, PERMZ, PORO and TOPS shape, finiteness and positivity checks.

The SPE9 include file copies PERMX to PERMY and PERMZ, then multiplies PERMZ by 0.01. The test suite asserts that result, not just that a parser returned a number.

No native SPE9 run yet. The static grid and tables load; the wells, controls and 900-day schedule do not. SPE9 audit work still uses OPM Flow as the external reference through verify/rerun.py. Calling this an in-house SPE9 simulation would be false.

How to check it

cd engine
python3 -m unittest -v test_deck_tables
python3 -m unittest -v test_provenance test_forecast test_geology test_fields
python3 selftest.py

test_deck_tables.py covers include expansion, missing/cyclic includes, COPY/MULTIPLY, the SPE9 grid, SPE9 PVT/relperm values, rejection of non-monotonic tables, and the SPE1 default-equivalence check. The full engine suite remains green at 86 tests; the selftest remains 11/11.

Limits you should state

  • No native SPE9 schedule or time-stepping. The static grid and properties are ready; the well model and 900-day driver are not.
  • No corner-point geometry. COORD, ZCORN and EGRID-based full-field grids remain future work.
  • One table per keyword. Multiple PVT/rock regions and EQUALS are not dispatched yet.
  • Piecewise-linear interpolation. Derivatives are one-sided at exact table knots, the same convention as the SPE1 path.
  • This is a property/static-grid proof, not a new validation case. It does not claim an SPE9 history match or a match to the OPM reference.
