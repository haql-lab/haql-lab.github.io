Feature: parallel ensemble execution · Engine surface: run_uncertainty.py · Status: shipped

Why it exists

A geological uncertainty study is not one simulation. It is tens or hundreds of simulations, each with a different permeability field, structure, contact or scalar sample. Running them one after another wastes the machine.

The engine's solver is intentionally single-threaded and Python/NumPy. Rather than pretending it is an MPI code, ensemble execution uses process-level concurrency: each realization is a normal run_spe1.py process with its own run ID, manifest and JSON output.

Usage

python3 run_uncertainty.py \
  --input uncertainty_input.example.json \
  --out /tmp/haql-ensemble \
  --T 365 \
  --workers 4

Everything else is unchanged. --workers defaults to 1, so existing scripts and regression tests keep the sequential behavior. Values below 1 are rejected.

OptionBehavior
--workers 1Sequential execution, identical to the previous driver behavior.
--workers NAt most N realizations run at once, capped by the number of pending realizations.
--dry-runNo solver processes; workers have no effect.
--resumeMatching completed runs are reused before the pool starts; only pending realizations are submitted.

How it works

  1. Generate all realizations first. Each one is written to realizations/ and hashed before execution.
  2. Classify work. Dry-run entries are recorded only. Matching --resume entries are reused only if experiment, realization hash, time settings and tolerance settings match.
  3. Submit pending jobs. A bounded ThreadPoolExecutor launches run_spe1.py subprocesses. Threads only coordinate process I/O; the solver itself does not share memory between realizations.
  4. Record as each finishes. The main thread updates experiment.json atomically after every completion, preserving an interrupted-run record.
  5. Sort the final results. Regardless of completion order, experiment.json and the forecast input use realization index order.

Safe boundary: realizations are independent. There is no shared mutable solver state, no cross-realization Newton coupling and no race on a run directory because each process writes its own files.

Determinism

Parallel completion order is nondeterministic. Result order is not. The driver sorts by realization_index before writing the final experiment and forecast input.

  • Every realization keeps its own deterministic seed sequence.
  • Every run keeps its own provenance manifest and run ID.
  • The forecast input lists runs in realization order, not completion order.
  • The regression test checks that two workers still produce real-0000 before real-0001 in the experiment record.

This does not make the wall-clock output byte-identical across worker counts. It makes the experiment's logical ordering and provenance stable.

Failures and resume

A failed subprocess is not removed. If run_spe1.py produces no JSON, the driver writes a parseable failure artifact at the expected run path, records the exit code and error, and continues with the remaining realizations.

When the pool finishes, the experiment status is completed only if every realization completed and passed its material-balance gate. Otherwise it is partial, and the command exits 3. A later --resume run can reuse the good artifacts and retry the failed or missing ones.

Do not judge an ensemble by its average alone. A failed or water-filled realization can be the one that matters. The experiment record keeps it visible for exactly that reason.

Resource guidance

ResourceRecommendation
CPUStart with --workers 2 on a 2-core laptop; use N ≤ physical cores for a shared machine.
MemoryEach worker is a separate Python process. Budget the solver's per-run memory times the worker count.
DiskEvery realization writes a run JSON, log and provenance manifest. Clean old experiment output deliberately; do not delete evidence mid-run.
Provenance storeWorkers write distinct run directories. Use a dedicated --store for large ensembles so experiments do not mix.
Solver speedParallelism does not make one run faster. It only overlaps independent runs.

Test evidence

The regression suite includes a two-realization, two-worker run against the SPE1 deck. It asserts:

python3 -m unittest -v \
  test_geology.TestCLI.test_parallel_workers_run_ensemble
  • exit code 0 when both realizations complete;
  • n_completed == 2 and n_failed == 0;
  • experiment records are ordered 0, 1;
  • both runs are completed;
  • the forecast input exists.

Run the full suite before trusting a larger ensemble:

python3 test_geology.py
python3 test_forecast.py
python3 test_provenance.py
python3 selftest.py

What this feature is not

  • Not solver parallelism. Each solve is still single-threaded; no MPI, no GPU, no domain decomposition.
  • Not distributed computing. Workers run on one host. A cluster/Slurm backend is a separate feature.
  • Not a speed guarantee. Oversubscribing cores or memory will make the ensemble slower.
  • Not a replacement for a scheduler. Large production runs still belong in a job scheduler with checkpoint/restart and resource limits.

Next infrastructure step: a scheduler adapter (Slurm/Kubernetes) and per-realization resource accounting. That is not part of this commit.
