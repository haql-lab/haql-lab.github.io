haql-engine · feature guide

Same physics. Better derivatives.

Every Newton step needs to know which way the equations are heading. The engine now calculates that direction from formulas instead of measuring it by repeatedly perturbing the model. The result is the same black-oil physics, a shorter run, and one less numerical approximation in the loop.

Feature: analytic three-phase Jacobian · Available in blackoil_vs.py, run_spe1.py and run_blackoil_vs.py · Status: shipped

The idea, in one sentence

A reservoir simulator solves a large set of equations by making a guess, measuring how wrong it is, and then taking a better guess. To take that better guess it needs the slope of every equation with respect to every unknown. That table of slopes is called the Jacobian.

There are two ways to get the slopes:

Finite difference Measure the slope

Nudge each unknown a tiny amount, rerun the equations, and divide the change in the answer by the nudge. It works, but it needs many extra evaluations and it is only an approximation.

Analytic Calculate the slope

Differentiate the equations once, by hand and in code. The slopes come from the same formulas the equations already use, without nudging the model.

The new path calculates the slopes for the full three-phase, variable-switching black-oil model: oil, water, free gas, dissolved gas, gravity, wells, porosity compressibility and fault-face transmissibility. The equations themselves are unchanged.

This is a solver improvement, not a new geological model. The answer is still constrained by the same equations and the same mass-balance gate.

Why the old way was slow

The SPE1 benchmark has 300 cells. Each cell carries three unknowns — pressure, water saturation, and either gas saturation or dissolved gas. That is roughly 900 unknowns. A dense finite-difference Jacobian would need two extra evaluations for every unknown: about 1,800 per Newton step.

The engine already used a distance-2 colouring trick. Cells that cannot affect the same equations are nudged together, so one pass covers many unknowns. That cut the work from 1,802 evaluations to 68 — a measured 26.5× saving. It was exact against the dense check, but it was still measuring slopes rather than calculating them.

The catch: a finite difference has a truncation error and a round-off floor. Near a sharp change in a table, the measured slope can be noisy, and the solver can stop earlier than the equations deserve. The old full SPE1 run needed 143 steps and 504–618 seconds.

What changed

The production solver now assembles the Jacobian from three groups of derivatives:

Part of the equationWhat is differentiated
What is stored in each cellPorosity as pressure changes; oil, water and gas volumes; dissolved gas; the switch between free gas and dissolved gas.
Flow between cellsOil, water and gas mobility; upstream-cell selection; pressure differences; gravity; phase density changes; fault-face multipliers.
Wells and controlsBHP source terms; producing and injecting phases; the rate constraint; the well-BHP unknown.

The result is a sparse matrix: it stores only the connections that can be nonzero. On the final SPE1 step the Jacobian has 6,848 stored entries. A dense matrix of the same size would have about 811,000.

An analytic build takes 0.030 s on a 300-cell test state, against 0.155 s for the coloured finite-difference build. More importantly, it makes zero extra equation evaluations to build the slopes. The old path still exists as an independent check, but production runs no longer use it.

What did not change

This matters as much as the speed-up. The feature is deliberately narrow:

  • The physics is the same. Same black-oil equations, same PVT and relative-permeability tables, same gravity, same Peaceman well model.
  • The conservation gate is the same. The full run still has to close oil, water and gas within 1e-6 relative material balance.
  • Variable switching is the same. A cell still switches between free gas and dissolved gas by conserving the gas component.
  • Fault barriers are the same. Per-face transmissibility multipliers enter the flux and its derivative exactly as before.
  • The evidence is the same. The committed SPE1 fixture and its provenance manifest were regenerated with the analytic path, so the published numbers and the current code agree.

The finite-difference builders remain in the code as oracles: independent ways to check the analytic result. They are not the production path.

The honest speed statement: on this two-core machine, OPM Flow still finishes SPE1 in 14.8 s, so the engine is about 3.3× slower at the 1e-6 gate. That is a large improvement from 26–42×, but it is not a claim to be faster than a production simulator.

The awkward part: corners in the tables

The fluid and rock properties come from tables: oil formation volume factor, gas solubility, viscosity, relative permeability. Between table points the engine interpolates in straight lines. At a table point, the straight line changes slope. There is no single derivative at that corner.

The same thing happens when the upstream cell changes: the flow direction flips, and the mobility switches from one cell to the other. The flux itself is continuous through the flip, but the derivative is not unique at the exact crossing.

The analytic path chooses a one-sided derivative: it uses the interval selected by the same search that the interpolator uses. It does not smooth the tables and it does not invent a derivative for the discrete upstream selector. This is the standard Newton linearisation for a piecewise-linear model. It can still cost an iteration if the state sits exactly on a corner, but it keeps the step defined and reproducible.

How to check it

The feature is exercised by the fast suite and by two independent slope checks:

cd engine
python3 selftest.py                 # 11 checks, about 4 s
python3 validate_jacobian_vs.py     # analytic vs central FD, four branches
python3 validate_jacobian.py        # two-phase analytic vs central FD

# Full 3,285-day SPE1 run, about 50 s
python3 run_spe1.py --T 3285 --quiet --strict \
  --json fixtures/spe1_full.json
python3 compare_spe1.py --run fixtures/spe1_full.json

The committed fixture records the analytic build count, the sparse size and the dense finite-difference work that was avoided. The provenance manifest seals the input, code identity and output hashes, so a regenerated run can be checked rather than taken on trust.

Limits you should state

  • It does not improve the geological match. The OPM comparison is still about 3.1% on cumulative oil. Analytic derivatives make the solve faster and cleaner; they do not fix relative-permeability or upscaling differences.
  • It is not a speed record. The engine remains single-threaded Python and is slower than OPM Flow. The claim is the measured 49.0 s at the 1e-6 gate on this host, not a general throughput promise.
  • It is not a global convergence proof. Four test branches and the full SPE1 conservation run are strong evidence, not a guarantee for every possible state or deck.
  • Corners remain corners. At an exact table knot or upstream flip the derivative is one-sided. A run can still need an extra Newton iteration there.
  • The scope is still narrow. Cartesian SPE1-class grids; no corner-point/EGRID, no SPE9, no full SCHEDULE parser, no history matching.
  • One machine, one case. The timings are from the two-core reference host. Absolute times will differ elsewhere; the relative comparison and the conservation result are the reproducible parts.

Do not present this as an accuracy upgrade. Present it as a solver upgrade with the same physics and the same conservation gate, verified against the old finite-difference path.

Questions

Does the engine use a different reservoir model now?

No. The residual equations, PVT tables, relative permeability, wells and fault barriers are unchanged. Only the way the solver computes the derivatives of those equations changed.

Why keep the finite-difference code if it is slower?

It is an independent oracle. If the analytic derivative has a sign error or a missed term, the finite-difference comparison is likely to catch it. Keeping both makes the faster path easier to defend.

Does the full SPE1 answer change?

Only slightly. Final cumulative oil differs by 0.0015% from the pre-analytic run, because the Newton path and stopping point differ at round-off level. The material-balance result and the comparison with OPM Flow are effectively unchanged.

Is 49 seconds fast?

It is about 10–12× faster than the previous tight-tolerance run on the same host, but still about 3.3× slower than OPM Flow. It makes the engine practical for small verification studies; it does not make it a full-field production simulator.

What happens at a table corner?

The code uses a one-sided derivative from the selected interpolation interval. The flux is continuous, so the Newton step remains defined. A state exactly on a corner can be less smooth than one between corners.
