haql-engine · Simulation audit

A forecast is not evidence. An audit is.

haql-engine is a from-scratch three-phase black-oil engine and an independent audit for Eclipse and OPM runs. It checks the run's own mass balance, convergence, reproduction and input integrity — and publishes the misses, including the ones it finds in public field data.

What it is

An engine for checking the physics. An audit for checking the run.

Two pieces, one purpose: make a simulation result something a reviewer can sign. The engine is the independent implementation; the audit reads a delivered deck and run and tests what the simulator itself claims.

The engine

Three-phase black oil — oil, water, free gas and dissolved gas — with implicit finite volumes, TPFA fluxes, upstream mobility, Peaceman wells, variable switching between Sg and Rs, and an analytic three-phase Jacobian. Python/NumPy, one CPU thread, Cartesian grids. It is a verification instrument, not a production simulator. See how the analytic Jacobian works →

The audit

Reads the deck and the run's own summary/restart output. Checks field material balance at 1e-6, convergence and solver-log health, cell-by-cell reproduction against a reference, and input integrity (PVT, relperm, grid, units, schedule, duplicate well definitions). Emits Markdown, PDF and JSON with a SHA-256 provenance manifest, and a report ID derived from the content of the inputs — not from wherever the audit happened to run.

The audit does not simulate. When a run lacks balance vectors, it can instrument the deck with output-only vectors and re-run it in OPM Flow — and it records both runs. When a gate cannot be evaluated, it reports UNKNOWN; it never passes by default.

Reproducible by construction

Same evidence, same verdict, on any machine.

An audit that cannot be re-run years later is an opinion. The toolchain now proves its own reproducibility, in your environment, on the evidence you sent.

Provenance receipts

Every run writes a manifest: SHA-256 of the deck, every INCLUDE file, the pre-registered gates — and with --hash-run, the entire run and reference tree. Paths are recorded machine-independently (relative, forward-slash), so the same evidence tree hashes identically on Linux, Windows and macOS.

Content-derived report ID

The report ID is the hash of what was audited, not of where it sat on a filesystem. Relocate the evidence tree, or re-run the audit on a different machine, and the ID still matches.

No hidden clock

By default no wall-clock timestamp enters the report — re-runs are byte-stable. If the client wants a date on the deliverable, it is passed explicitly (--stamp), never picked up from the environment.

Selfcheck and doctor

--selfcheck runs the complete audit twice and requires byte-identical Markdown and JSON — on your machine, in front of you. doctor.py prints the environment passport and validates the invariants the audit depends on.

Revision diff

deckdiff.py answers the real quarterly question: what changed between forecasts. Every changed keyword is classed into GRID / PVT / relperm / SOLUTION / schedule, and a physics-class change hard-fails — a silent model swap cannot be waved through as "minor updates".

Ensembles and pinned references

ensemble.py audits every history-match realisation with the identical pre-registered gates and reports the worst run, not the average — plus the residual spread. Your ground-truth run is pinned by SHA in the reference library with drift detection, so every later audit can be proved to use the same reference.

Try it on your own machine: python3 verify/doctor.py, then python3 verify/audit.py --deck CASE.DATA --run RUN/ --selfcheck. The selfcheck runs the audit twice and fails loudly if the outputs differ by a single byte.

Honest limits

What this is not.

  • Not a replacement simulator. SPE1 only; no SPE9, no corner-point/EGRID, no real field grids yet. Cartesian grids, single-threaded Python. The engine is a cross-check, not a development-planning tool.
  • Not faster. About 3.3× slower than OPM Flow on SPE1 at the 1e-6 mass-balance gate (49.0 s vs 14.8 s). The analytic Jacobian removed the finite-difference tax, but this is not a throughput claim.
  • Not a geology or reserves audit. The audit checks numerical and input integrity. It does not judge upscaling, SCAL, hysteresis, history match, or whether the field will produce what the model says.
  • No client field audit yet. The Norne case is public; it is not a client engagement. The first client audit is priced and scoped as a pilot, with success criteria signed before work starts.
  • UNKNOWN is not PASS. OPM's release log does not print scaled residuals, so convergence is often UNKNOWN; the audit says so and reports the log-health proxy separately.

FAQ

Straight answers.

Does haql-engine replace Eclipse or CMG?

No. It audits their output and cross-checks the physics. The engine is an independent implementation for verification, not a production simulator; it supports SPE1-class Cartesian decks today, not full-field corner-point models.

Is it faster?

Relative to its own previous version, yes: the analytic Jacobian cut the full SPE1 run from 504–618 s to 49.0 s at the 1e-6 gate. Relative to OPM Flow, no — OPM Flow takes 14.8 s on the same host, so the engine is about 3.3× slower. The value is independent verification, not speed.

What exactly does the audit check?

Field material balance from the run's own in-place and cumulative vectors; Newton convergence and solver-log health; cell-by-cell pressure, saturation, BHP, oil rate and water cut against a reference; and input integrity — PVT, relperm, grid, units and schedule. It does not judge geology, upscaling, SCAL or history match.

What if my run has no balance vectors?

The audit can instrument the deck with output-only FOIP/FWIP/FGIP vectors and re-run it in OPM Flow, then audit the re-run. The report records both runs and says the re-run is an independent reproduction, not your original run. Without that, the gate is UNKNOWN, not passed.

Can we reproduce an audit years later?

Yes, and it is designed for that. Every audited input is hashed into a provenance manifest (deck, every INCLUDE file, the gates; the full run tree with --hash-run). The report ID is derived from that content, so relocating the evidence or moving machines does not change it. --selfcheck re-runs the audit twice and requires byte-identical output; doctor.py prints the environment passport. No wall clock enters the report unless you explicitly stamp a date.

We re-run our history match every quarter. Can you audit all of it?

That is the intended cadence. ensemble.py audits every realisation with the same pre-registered gates in sorted, auditable order and reports the worst run and the residual spread — a match fair on average but loose on individual realisations is flagged. deckdiff.py then diffs this quarter's deck against the last: input or schedule changes are listed value-by-value, and any physics-class change fails the audit so a silent model swap cannot pass. Your pinned reference run is stored by SHA and proved unchanged at every use.

What if a forecast revision quietly changed the model?

The diff audit classes every changed keyword (grid, PVT, relperm, solution section versus schedule) and exits as a failure when the physics class moved. Value-level tables show exactly which numbers moved and by how much, including repetition defaults.

Has a client used it?

Not yet. The evidence on this page is from the public SPE1 benchmark and Equinor's public Norne field case. The first client engagement is a pilot, with success criteria signed before work starts.
